# 文件上传与异步处理架构设计文档 (从本地演进至云原生)

在产品实验和早期开发阶段，采用 **本地文件系统（Local File System）+ 单体异步处理** 的架构是非常务实的选择。这既降低了环境配置的复杂度，方便本地打断点调试，又省去了前期的云资源开销。

为了保证未来能平滑无缝地迁移到 **“OSS直传 + FC异步解压处理”** 的高级云原生架构，我们在系统设计时严格遵循了依赖倒置原则（DIP）和事件驱动架构（EDA）。

---

## 一、 架构核心设计思想

* **物理存储与逻辑记录解耦：** 数据库绝对不存储带有具体盘符或域名的绝对路径（如 `D:/files/...` 或 `http://oss...`），只存储一个相对的抽象标识符 `file_key`（例如：`2026/08/26/a1b2.pdf`）。
* **存储策略化（Strategy Pattern）：** 定义标准的 `StorageService` 接口。当前使用 `LocalStorageImpl` 实现，未来只需增加 `OssStorageImpl` 并在配置文件中切换即可。
* **异步事件解耦（Event-Driven）：** 文件上传主流程只负责“保存物理文件 + 记录数据库状态为‘待处理’”，随后发布一个领域事件（Spring Event）。由独立的异步监听器去执行耗时的“文件转 Markdown”逻辑，从而保证接口极速响应。

## 二、 核心数据模型设计 (PostgreSQL)

根据以下示例表的内容更新系统的资源表（resources）。

```sql
CREATE TABLE sys_files (
    file_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,                  -- 上传用户
    original_name VARCHAR(255) NOT NULL,      -- 原文件名，例如: "测试报告.pdf"
    file_key VARCHAR(500) NOT NULL,           -- 物理存储标识，例如: "2026/08/26/uuid.pdf"
    file_size BIGINT NOT NULL,                -- 文件大小(字节)
    file_type VARCHAR(50) NOT NULL,           -- 文件MIME类型，如 application/pdf
    
    -- 异步转换处理相关字段
    process_status SMALLINT NOT NULL DEFAULT 0, -- 0-待处理, 1-处理中, 2-处理成功, 3-处理失败
    md_file_key VARCHAR(500) DEFAULT NULL,      -- 转换成功后的 Markdown 文件存储标识
    error_message TEXT DEFAULT NULL,            -- 如果失败，记录错误原因
    
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_user_id ON sys_files(user_id);

```

## 三、 核心接口设计 (Java Spring Boot)

### 1. 存储服务接口设计 (`StorageService.java`)

规范文件的上传、下载和访问。无论底层是本地硬盘还是 OSS，都必须实现该接口。

```java
public interface StorageService {
    /**
     * 上传文件
     * @param inputStream 文件输入流
     * @param originalFilename 原始文件名 (用于提取后缀)
     * @return 抽象存储标识符 (file_key)
     */
    String store(InputStream inputStream, String originalFilename);

    /**
     * 获取文件的字节流 (供后续解析 Markdown 使用)
     */
    InputStream getAsInputStream(String fileKey);

    /**
     * 获取文件的可访问 URL (本地模式返回接口地址，OSS模式返回签名URL)
     */
    String getAccessUrl(String fileKey);
}

```

### 2. 文档解析接口设计 (`DocumentProcessor.java`)

规范文件处理逻辑，当前核心是转换为 Markdown。

```java
public interface DocumentProcessor {
    /**
     * 判断是否支持该类型文件解析
     */
    boolean supports(String fileType);

    /**
     * 将源文件流转换为 Markdown 内容
     */
    String convertToMarkdown(InputStream sourceStream);
}
```

## 四、 实验阶段的具体实现 (Local 模式)

### 1. 存储接口的本地实现

将文件存储在服务器的指定目录（如 `/opt/crm/data` 或 `D:/crm/data`）。通过 UUID 打散，避免文件名冲突。

```java
@Service
@ConditionalOnProperty(name = "storage.type", havingValue = "local", matchIfMissing = true)
public class LocalStorageServiceImpl implements StorageService {
    
    @Value("${storage.local.base-path:/opt/crm/data}")
    private String basePath;

    @Override
    public String store(InputStream inputStream, String originalFilename) {
        // 生成散列目录 2026/08/26/
        String datePath = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy/MM/dd"));
        String extension = StringUtils.getFilenameExtension(originalFilename);
        String uuid = UUID.randomUUID().toString().replace("-", "");
        // 最终相对路径： 2026/08/26/uuid.pdf
        String fileKey = datePath + "/" + uuid + "." + extension;
        
        Path targetLocation = Paths.get(basePath).resolve(fileKey);
        try {
            Files.createDirectories(targetLocation.getParent());
            Files.copy(inputStream, targetLocation, StandardCopyOption.REPLACE_EXISTING);
            return fileKey;
        } catch (IOException e) {
            throw new RuntimeException("本地文件存储失败", e);
        }
    }
    
    @Override
    public InputStream getAsInputStream(String fileKey) {
        try {
            return Files.newInputStream(Paths.get(basePath).resolve(fileKey));
        } catch (IOException e) {
            throw new RuntimeException("文件读取失败", e);
        }
    }

    @Override
    public String getAccessUrl(String fileKey) {
        // 本地模式返回代理下载接口的 URL
        return "http://localhost:8080/api/files/download?key=" + fileKey;
    }
}

```

### 2. 上传主干流程与事件发布

在 Controller 和 Service 层面，只做同步保存，保证接口能在几十毫秒内返回，不阻塞用户操作。

```java
@Service
public class FileAppService {

    @Autowired
    private StorageService storageService;
    @Autowired
    private SysFileMapper sysFileMapper; // 假设使用 MyBatis 或 JPA
    @Autowired
    private ApplicationEventPublisher eventPublisher;

    @Transactional
    public SysFile uploadAndTriggerProcess(MultipartFile file, Long userId) throws IOException {
        // 1. 调用存储策略保存物理文件
        String fileKey = storageService.store(file.getInputStream(), file.getOriginalFilename());
        
        // 2. 写入数据库，状态为 "待处理" (STATUS=0)
        SysFile sysFile = new SysFile();
        sysFile.setUserId(userId);
        sysFile.setOriginalName(file.getOriginalFilename());
        sysFile.setFileKey(fileKey);
        sysFile.setFileSize(file.getSize());
        sysFile.setFileType(file.getContentType());
        sysFile.setProcessStatus(0); 
        sysFileMapper.insert(sysFile);

        // 3. 抛出基于 Spring 的领域事件（业务解耦的关键）
        eventPublisher.publishEvent(new FileUploadedEvent(this, sysFile.getFileId()));
        
        return sysFile;
    }
}

```

### 3. 异步监听与 Markdown 处理

利用 Spring 的 `@Async` 实现异步解耦，在这里进行耗时的文档解析逻辑。

```java
@Component
public class FileProcessListener {

    @Autowired
    private SysFileMapper sysFileMapper;
    @Autowired
    private StorageService storageService;
    @Autowired
    private DocumentProcessor documentProcessor;

    // 开启异步线程处理
    @Async("fileProcessExecutor") // 建议自定义线程池避免耗尽主线程
    @EventListener
    public void onFileUploaded(FileUploadedEvent event) {
        Long fileId = event.getFileId();
        SysFile sysFile = sysFileMapper.selectById(fileId);
        if (sysFile == null) return;

        try {
            // 1. 更新状态为 "处理中"
            sysFileMapper.updateStatus(fileId, 1, null, null);
            
            // 2. 获取源文件流
            InputStream sourceStream = storageService.getAsInputStream(sysFile.getFileKey());
            
            // 3. 解析为 Markdown 字符串 (耗时操作)
            String mdContent = documentProcessor.convertToMarkdown(sourceStream);
            
            // 4. 将生成的 Markdown 内容再次存储，获取新的 md_file_key
            InputStream mdStream = new ByteArrayInputStream(mdContent.getBytes(StandardCharsets.UTF_8));
            String mdFileName = sysFile.getOriginalName() + ".md";
            String mdFileKey = storageService.store(mdStream, mdFileName);
            
            // 5. 更新状态为 "处理成功"
            sysFileMapper.updateStatus(fileId, 2, mdFileKey, null);
            
        } catch (Exception e) {
            // 6. 更新状态为 "处理失败"
            sysFileMapper.updateStatus(fileId, 3, null, e.getMessage());
        }
    }
}

```

## 五、 未来的平滑演进路线 (To OSS + FC)

当产品度过实验期，面临真实用户的并发上传时，后端核心业务代码几乎不需要改动，只需做以下调整即可向“OSS + FC”架构演进：

* **新增 `OssStorageServiceImpl`：** 实现 `StorageService`，内部调用阿里云 OSS SDK，并将配置文件中的 `storage.type` 改为 `oss`。
* **流量旁路（前端改造）：** 增加一个获取 STS 凭证的接口。前端不再将文件通过 HTTP POST 发给 Java 后端，而是直接传给 OSS，解放服务器带宽。
* **事件源变更（由 FC 触发）：**
* **当前架构：** `FileUploadedEvent` 是在 Java 后端上传完毕后自行触发的。
* **演进后：** 由于文件是前端直接传 OSS 的，Java 后端只需暴露一个 `WebhookController`。阿里云 FC 解压或处理完毕后调用该 Webhook，Webhook 接口在接收到请求后，手动发布 `FileUploadedEvent` 即可。后续的处理逻辑完全复用。

这种设计模式充分保证了实验阶段的开发效率与商业化阶段的架构弹性，没有任何“抛弃重写（Throw-away code）”的浪费
