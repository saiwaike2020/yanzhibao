这是一份基于您需求的“简历解析、AI结构化提取与向量化检索”详细系统设计方案。

本方案结合了传统的**关系型数据库管理**与当前主流的 **RAG（检索增强生成）/ 向量搜索** 架构。考虑到前文已经使用了 PostgreSQL，我们强烈建议引入 PostgreSQL 的 **`pgvector`** 插件，这样可以在同一个数据库中完美实现“元数据过滤 + 向量相似度检索 + 基础信息联合查询”，极大降低系统复杂度。

---

### 一、 整体架构与技术选型

1. **文档格式化转换 (PDF/Word -> Markdown)**：
* *技术推荐*：使用开源工具如 `Apache Tika` 提取文本，或使用更现代的文档解析引擎如 `unstructured.io`、`MinerU` (支持极好的版面分析转 MD)。


2. **个人信息提取与内容脱敏 (LLM 结构化输出)**：
* *技术推荐*：引入大语言模型 (如 Qwen、DeepSeek 或 OpenAI)，通过 Prompt 要求其提取姓名、电话等信息，并返回**剔除敏感信息后的剩余文本**。


3. **文本向量化 (Embedding)**：
* *技术推荐*：使用 BAAI/bge-m3、阿里 DashScope Text Embedding 或 OpenAI `text-embedding-3-small`，将脱敏后的 MD 内容转化为高维浮点数组（向量）。


4. **混合存储与检索引擎**：
* *技术推荐*：**PostgreSQL + `pgvector` 扩展**。利用 SQL 即可完成高维向量的近邻搜索 (KNN/ANN)，并直接 `JOIN` 业务表。框架层推荐使用 **Spring AI** 或 **LangChain4j**。

### 二、 数据库设计 (PostgreSQL + pgvector)

开启向量支持：`CREATE EXTENSION IF NOT EXISTS vector;`

#### 1. 基础信息表 (`resume_base_info`)

用于记录文件原始上传状态和最基本的文件属性。

```sql
CREATE TABLE resume_base_info (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    uploader_id BIGINT NOT NULL,              -- 上传人ID
    original_file_name VARCHAR(255) NOT NULL, -- 原始文件名 (如: 张三_Java工程师.pdf)
    file_path_key VARCHAR(500) NOT NULL,      -- 物理存储路径 (OSS key或本地相对路径)
    file_type VARCHAR(50),                    -- pdf, docx
    process_status SMALLINT DEFAULT 0,        -- 0-待处理, 1-处理中, 2-成功, 3-失败
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

```

#### 2. 解析与向量索引表 (`resume_parsed_data`)

存储结构化元数据以及脱敏后的 Markdown 向量。

```sql
CREATE TABLE resume_parsed_data (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    resume_id BIGINT NOT NULL REFERENCES resume_base_info(id), -- 关联基础表ID
    
    -- 提取出的元数据 (个人隐私信息 PII)
    candidate_name VARCHAR(100),              -- 姓名
    birth_date VARCHAR(50),                   -- 出生年月
    phone_number VARCHAR(50),                 -- 手机号
    email VARCHAR(100),                       -- 邮箱
    
    -- 剩余 MD 内容与向量
    anonymized_md_content TEXT,               -- 脱敏后的MD纯文本
    content_vector vector(1024),              -- MD内容的向量表示 (维度取决于选用的Embedding模型，如1024或1536)
    
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 为向量字段创建 HNSW 索引以加速检索 (余弦相似度)
CREATE INDEX ON resume_parsed_data USING hnsw (content_vector vector_cosine_ops);

```

### 三、 核心处理工作流 (Async Workflow)

复用上一节的事件驱动架构，在监听到 `FileUploadedEvent` 后，进入如下处理流：

#### Step 1: 文档转 Markdown (Parse)

将上传的 PDF/Word 转化为带有结构（标题、列表）的 Markdown。Markdown 能很好地保留简历的逻辑结构（如“教育经历”、“工作经验”等节点），有助于后续的大模型理解。

#### Step 2: 信息抽取与脱敏 (Extraction & Anonymization)

传统的正则表达式很难应对各种奇形怪状的简历。建议直接调用 LLM，定义 JSON Schema 强制其输出所需结构。

**Prompt 设计示例：**

> "你是一个专业的HR简历解析助手。请阅读以下简历的 Markdown 内容，完成两个任务：
> 1. 提取候选人的基本信息：姓名、出生年月、手机、邮箱。
> 2. 将原文中的这四类隐私信息替换为 `[脱敏]`，并输出**剩余的 Markdown 内容**。
> 请严格按照以下 JSON 格式返回结果：
> `{ "name": "...", "birth_date": "...", "phone": "...", "email": "...", "anonymized_md": "..." }`"
> 
> 

#### Step 3: 文本向量化 (Embedding)

拿到大模型返回的 `anonymized_md`（剩余 MD 内容）后，调用 Embedding 模型（例如：`text-embedding-v2`），将这段文本转化为长度固定的浮点数数组。
*优化提示*：如果剩余简历 MD 内容极长（超过 Embedding 模型的 Token 限制），可按标题将其进行 Chunk（切块）处理，存入多行，但通常普通简历的长度在 8k tokens 内，可直接整篇向量化。

#### Step 4: 事务入库 (Persistence)

在一个数据库事务中：

1. 将解析出的元数据、脱敏MD、向量组装成实体，插入 `resume_parsed_data`，并带上 `resume_id`。
2. 更新 `resume_base_info` 的 `process_status` 为 2（成功）。

### 四、 代码架构实现 (Java Spring Boot 伪代码)

#### 1. 简历处理异步监听器

```java
@Component
public class ResumeProcessListener {
    
    @Autowired
    private LlmService llmService; // 封装了大模型调用
    @Autowired
    private EmbeddingModel embeddingModel; // 封装了向量化调用
    @Autowired
    private ResumeRepository resumeRepository;
    
    @Async
    @EventListener
    public void handleResumeUpload(FileUploadedEvent event) {
        Long resumeId = event.getFileId();
        
        try {
            // 1. 转为 MD
            String rawMarkdown = convertToMarkdown(resumeId);
            
            // 2. LLM 信息抽取与脱敏
            ExtractedResumeDto extracted = llmService.extractAndAnonymize(rawMarkdown);
            
            // 3. 将脱敏内容进行 Embedding 向量化
            List<Double> vector = embeddingModel.embed(extracted.getAnonymizedMd());
            
            // 4. 入库存储
            resumeRepository.saveParsedData(resumeId, extracted, vector);
            
            // 5. 更新基础状态
            resumeRepository.updateStatus(resumeId, SUCCESS);
            
        } catch(Exception e) {
            resumeRepository.updateStatus(resumeId, FAILED);
        }
    }
}

```

#### 2. 向量检索与联合查询 API

这是系统的核心亮点，能够根据一段自然语言（如：“寻找有5年Java开发经验，熟悉微服务架构，做过金融项目的候选人”）来检索简历，并带出元数据。

**Dao层 (MyBatis 或 JdbcTemplate 实现)：**

```java
@Repository
public class ResumeSearchDao {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;

    /**
     * 混合检索：向量相似度匹配 + 联合基础信息
     */
    public List<SearchResultDto> searchResumes(String queryVectorString, int limit) {
        
        // 使用 pgvector 的 <=> 符号计算余弦距离，越小越相似
        String sql = """
            SELECT 
                b.id as original_file_id,
                b.original_file_name,
                b.file_path_key,
                p.candidate_name,
                p.phone_number,
                p.email,
                -- 1 - cosine_distance 即为相似度评分
                1 - (p.content_vector <=> ?::vector) as similarity_score 
            FROM resume_parsed_data p
            JOIN resume_base_info b ON p.resume_id = b.id
            ORDER BY p.content_vector <=> ?::vector
            LIMIT ?
        """;
        
        // pgvector 接受的格式为 "[0.123, 0.456, ...]"
        return jdbcTemplate.query(sql, 
            new Object[]{queryVectorString, queryVectorString, limit}, 
            new SearchResultRowMapper()
        );
    }
}

```

**Service层检索逻辑：**

```java
public List<SearchResultDto> search(String userCondition) {
    // 1. 将用户的自然语言搜索条件，转成同一个维度的向量
    List<Double> queryVector = embeddingModel.embed(userCondition);
    
    // 2. 将 List<Double> 格式化为 pgvector 识别的字符串格式
    String vectorStr = queryVector.toString(); 
    
    // 3. 执行 DB 向量搜索 + 联合查询 (Top 10)
    return resumeSearchDao.searchResumes(vectorStr, 10);
}

```

### 五、 方案优势总结

1. **隐私安全保护**：存入向量模型的是“脱敏后”的纯履历信息（技能、项目经验等），即使向量库被逆向，也无法还原出候选人的真实身份信息，符合极高的安全审计标准。
2. **极简架构（减少组件维护）**：由于使用了 PostgreSQL 的 `pgvector`，您**不需要**额外去搭建和维护像 Elasticsearch、Milvus 或 Qdrant 这样的独立搜索引擎或向量数据库。数据同步、事务一致性问题在单机库中不复存在。
3. **强大的混合检索能力**：未来您可以极其容易地在 SQL 中加入元数据过滤。例如：
`WHERE p.content_vector <=> ?::vector < 0.3 AND p.candidate_name LIKE '李%'`
这种**标量过滤 + 向量排序**的结合，是目前 AI 检索领域最佳的落地实践。
