# **CRM 系统用户管理与权限管理设计文档（v3）**

> **版本说明**
> - **v3.7（当前）**：新增「记录级有效期」——**所有业务表统一增加 `valid_from` / `valid_until`**，决定记录是否可用；业务上删除记录或使记录无效统一通过设置 `valid_until` 实现（逻辑失效，不做物理删除，详见 2.5）。
> - **v3.6**：新增「原所有者权限调整」——个人用户将资源所有权**分享（转让）给企业**后，企业管理员可将原用户的访问权限调整为**无权（NONE）/ 只读（READ）/ 可写（WRITE）**（详见 6.4 与用例 UC-034）。
> - **v3.5**：新增「审批流程」——①用户申请加入企业需企业所有者/管理员**批准**生效（UC-032）；②企业注销、企业所有权转让需系统管理员或有权限的审计人员**批准**生效（UC-033）；③企业用户创建资源时可**指定资源所有权归属个人或企业**（详见 6.3）。
> - **v3.4**：存储配额支持**个体专属调整**——系统管理员可针对单个用户或个别企业设置专属存储配额（`storage_quotas`，优先于全局默认配额，详见 2.4 与用例 UC-031）。
> - **v3.3**：新增「存储配额」——资源存储设有上限，按归属主体核算（个人默认 200MB、企业默认 10GB），系统管理员可通过系统参数动态调节（详见 2.4 与用例 UC-029 / UC-030）。
> - **v3.2**：新增「消息中心」——每个用户拥有独立消息中心，可接收系统消息；用户申请加入企业时自动通知企业管理员、企业邀请用户加入时自动通知被邀请用户（详见 4.8 与用例 UC-026 / UC-027 / UC-028）。当前**不通过短信发送额外提醒**，预留短信通知扩展点。
> - **v3.1**：新增「密码重置 / 忘记密码」功能——支持通过手机号 + 短信验证码重置登录密码（短信场景 `RESET_PWD`，详见 4.7 与用例 UC-025）。
> - **v3**：资源所有权模型调整——支持**多所有者**（资源可被多个用户或企业共同拥有）、**所有权转让**（所有者可将所有权转让给其他用户或企业）、**所有权有效期**（起始可用日期必填，过期时间可选，不设置则一直有效）；数据库设计同步调整（新增 `resource_owners` 表，`resources` 表不再持有 `owner_type/owner_id`）。
> - **v2**：上一版本基线。

## **1. 概述**

### **1.1 背景**

本设计用于 CRM 系统的用户管理、企业组织管理和资源权限管理。系统需要支持手机号验证码注册、微信快速注册、手机号密码登录、微信扫码登录，并支持企业内部分组与资源的细粒度权限控制。同时引入系统级用户角色（系统管理员、审计人员），实现系统级管理与审计日志查看权限的灵活分配。

### **1.2 设计目标**

- 支持手机号与微信两种注册、登录方式。
- 支持手机号 + 短信验证码重置密码（忘记密码找回），保障账号的可恢复性。
- 每个用户拥有**消息中心**，可接收系统消息；申请加入企业 / 企业邀请加入时自动向相关方推送站内消息，当前不通过短信额外提醒（预留短信通知扩展点）。
- 资源存储设有**配额上限**（个人默认 200MB、企业默认 10GB），系统管理员可动态调节。
- 支持普通用户、企业用户、系统用户三类用户身份。
- 企业内支持企业管理员、普通成员、分组管理员等角色。
- 企业内支持多级分组树状结构，但当前需求仅允许创建一级分组，后续可无缝扩展。
- 只有企业管理员可以创建分组，并支持将指定分组的管理权授予其他成员，实现分级授权。
- 资源模型支持资料库、文件夹、单个文件等细粒度资源类型。
- 支持对资源进行读、写、所有权三种权限控制。
- 资源可被**多个用户或企业**共同拥有，所有权可在**用户或企业之间转让**。
- 资源的读、写、所有权通过**起始可用日期**与**过期时间**控制有效期：起始可用日期必填，未设置过期时间则一直有效。
- 授权主体既可以是分组，也可以是单个用户。
- 支持数据行级权限，基于业务对象属性对数据行进行过滤。
- 组内成员自动继承分组的资源权限；用户直接授权与分组授权合并，取最高权限。
- 系统管理员作为系统最高权限角色，负责系统级管理与审计人员权限分配。
- 审计人员可查看审计日志，其查看范围可由系统管理员配置为部分或全部普通用户及企业用户的日志。
- 针对管理员角色的提权与降级（如设置其他用户为管理员、将管理员改为普通用户）等敏感高危操作，强制进行手机短信验证码校验，确保权限变更为本人授权。
- 保证权限模型清晰、可扩展、易审计。

| 术语 | 说明 |
| :--- | :--- |
| **用户 User** | 系统账号实体，可以是普通用户、企业用户或系统用户 |

| **企业用户** | 已加入某个企业的用户身份，其企业内角色由成员关系决定 |
| **系统用户** | 具有系统级管理或审计职责的用户，不参与企业业务，但可进行系统配置和审计查看 |
| **系统管理员 System Admin** | 系统中权限最高的用户，负责系统参数、用户管理、审计权限分配等 |
| **审计人员 Auditor** | 可查看系统中普通用户和企业用户的审计日志，其查看范围由系统管理员授权 |
| **企业 Company** | 租户，承载企业空间、成员、分组和资源 |
| **企业成员 Company Member** | 用户加入某企业后的身份关系 |
| **企业管理员 Company Admin** | 企业内具有管理权限的成员，分为所有者和管理员 |
| **分组 Group** | 企业内的组织单元，支持树状层级（当前仅一级） |
| **分组管理员 Group Leader** | 某个分组的管理员，可管理该组成员，但非企业级管理员 |
| **资源 Resource** | 企业或个人的数据资源，包括资料库、文件夹、文件三种类型 |
| **资料库 Library** | 资源容器，可包含文件夹和文件，是最上层的资源节点 |
| **文件夹 Folder** | 位于资料库内部的资源容器，可包含文件和子文件夹（可选） |
| **文件 File** | 具体的数据文件，是资源的叶子节点 |
| **资源权限 Resource Permission** | 对资源的操作许可，分为读、写、所有权 |
| **资源所有者 Resource Owner** | 拥有资源所有权的个人用户或企业；一个资源可被多个所有者共同拥有 |
| **所有权有效期 Ownership Validity** | 所有权的有效时间段，由起始可用日期与过期时间界定；起始日期必填，未设置过期时间则一直有效 |
| **资源权限有效期 Permission Validity** | 资源读/写/所有权授权的有效时间段，由起始可用日期与过期时间界定；起始日期必填，未设置过期时间则一直有效 |
| **记录有效期 Record Validity** | 所有业务记录的统一可用性模型：`valid_from`（生效起始时间，必填）与 `valid_until`（失效时间，为空表示一直有效）共同决定记录是否可用；记录删除或失效通过设置 `valid_until` 实现（逻辑失效，不做物理删除） |
| **所有权转让 Ownership Transfer** | 资源所有者将资源所有权转让给其他用户或企业的行为 |
| **数据行级权限 Row-level Permission** | 基于业务对象属性过滤数据行的权限规则 |
| **管理授权 Management Delegation** | 企业管理员将指定分组的管理权限授予其他成员的行为 |
| **授权主体 Grantee** | 权限授予对象，支持分组和用户 |
| **审计日志 Audit Log** | 记录系统内重要操作和事件的日志信息 |

## **2. 需求分析**

### **2.1 注册与登录需求**

- 支持手机号 + 短信验证码快速注册。
- 手机号快速注册时，用户需要设置个人密码。
- 支持微信号快速注册，并且需要提供手机号。
- 支持手机号 + 密码登录。
- 支持微信扫码登录。
- 支持手机号 + 短信验证码**重置密码**（忘记密码）：用户可通过已注册手机号接收验证码并设置新密码。

### **2.2 用户与组织需求**

- 用户分为 **普通用户**、**企业用户**、**系统用户** 三类。
  - 普通用户：注册后未加入任何企业的用户，可使用个人空间。
  - 企业用户：已加入一个或多个企业的用户，在企业内拥有相应角色。
  - 系统用户：包括 **系统管理员** 和 **审计人员**，不参与企业业务，拥有系统级权限。
- 系统管理员是系统中权限最高的用户，拥有系统级管理权限，包括用户管理、系统配置、审计权限分配等。
- 审计人员可以查看系统中普通用户和企业用户的审计日志，审计人员可以是多个，分别具有部分或者全部查看普通用户和企业用户的审计日志信息，由系统管理员来分配权限。
- 企业用户分为管理员和普通成员。
- 管理员可以是企业管理员，也可以是分组管理员。
- 企业内支持分组树状结构，但当前阶段仅允许创建一级分组，即分组内部不能再创建子分组；设计上预留层级字段以便后续扩展。
- 只有企业管理员能创建分组。
- 企业管理员可以将某个分组的管理权授予其他成员，使其成为该分组的管理员，实现分级授权。
- **安全与合规需求**：在管理员对其他成员进行角色提权（如设为企业管理员、分组管理员或系统角色）或降级（如将管理员调整为普通成员）时，系统需向当前操作的管理员手机号发送短信验证码，校验通过后方可完成变更，以防未经授权的权限提升与非法降级。

### **2.3 权限需求**

- 资源类型支持资料库、文件夹、单个文件等细粒度资源。
- 权限分为读权限、写权限、所有权。
- 资源权限可以授权给分组，也可以直接授权给单个用户。
- 组内成员自动获得分组对应的资源权限。
- 用户直接获得的权限与通过分组继承的权限合并，取最高权限。
- 资源可被多个用户或企业**共同拥有**，所有权可在用户或企业之间**转让**。
- 资源的读、写、所有权通过**起始可用日期**与**过期时间**控制有效期：起始可用日期必填，未设置过期时间则一直有效。
- 支持数据行级权限，例如根据业务对象属性（如所属地区、客户等级等）过滤数据行，实现同一资源内不同用户看到不同范围的数据。
- 企业创建的资源，企业默认成为资源所有者并拥有全部操作权限；资源所有者拥有该资源的全部权限。
- 系统管理员拥有系统级最高权限，可以管理系统用户、分配审计权限。
- 审计人员拥有查看审计日志的权限，其查看范围由系统管理员配置，可细粒度控制。

### **2.4 存储配额需求**

- 资源的存储容量设有**上限（配额）**，超出上限时禁止继续创建 / 上传文件。
- 配额按**归属主体**核算：
  - **个人存储**：归属于某个用户（`resource_owners` 中 `owner_type=USER`）的全部文件占用之和；
  - **企业存储**：归属于某个企业（`owner_type=COMPANY`）的全部文件占用之和。
- 默认配额：**个人存储上限 200MB，企业存储上限 10GB**。
- 存储上限由**系统管理员**通过系统参数动态调节，调节后立即生效。
- 配额以**字节**为单位存储与核算。
- 除全局默认配额外，系统管理员可针对**单个用户或个别企业**设置**专属配额**（`storage_quotas`），专属配额**优先于**全局默认配额。
- 未设置专属配额的主体使用全局默认配额。

### **2.5 数据生命周期与记录有效期**

- **所有业务表**统一维护两个时间字段，用于决定当前记录是否可用：
  - `valid_from`：记录**生效起始时间**（必填，默认创建时间，即创建即生效）；
  - `valid_until`：记录**失效时间**（可选，**为空表示一直有效**）。
- **有效性判定**：一条记录当前可用，当且仅当 `valid_from <= 当前时间 AND (valid_until IS NULL OR valid_until >= 当前时间)`。
- **删除 / 失效语义**：业务上删除记录或使记录无效（如注销用户、解散企业、移除成员、撤销授权、撤销分组、停用参数等），统一通过**设置 `valid_until = 当前时间`** 实现，**不做物理删除**，保留历史可追溯。
- **已有有效期语义的表**：资源所有权（`resource_owners`）、资源显式授权（`resource_permissions`）已按该模型设计，直接沿用；其余全部业务表统一纳入。
- 各业务查询默认仅返回**当前有效**（满足有效期区间）的记录。

## **3. 总体设计**

### **3.1 核心模型关系**

核心实体关系如下：

```text
用户 User（包含手机号 phone）
├─ 认证标识 UserAuth（手机号、微信）
├─ 企业成员关系 CompanyMember
│  └─ 企业 Company
│     ├─ 分组 Group（树状结构，当前仅一级）
│     │  └─ 分组成员 GroupMember（普通组员/分组管理员）
│     ├─ 资源 Resource（资料库/文件夹/文件）
│     │  ├─ 资源所有者 ResourceOwner（多所有者：用户/企业，含有效期，支持转让）
│     │  └─ 资源权限 ResourcePermission（授权给分组或用户）
│     └─ 管理授权 ManagementDelegation（分级授权）
├─ 系统角色 SystemRole（系统管理员、审计人员）
│  └─ 审计权限 AuditPermission（审计日志查看范围）
├─ 个人资源 Resource（个人资料库等）
├─ 系统参数 SystemSetting（存储配额默认上限等系统级配置）
└─ 个体存储配额 StorageQuota（单个用户/企业的专属存储上限）

数据行级权限 RowPermission
├─ 关联资源 Resource
├─ 授权主体 Grantee（分组或用户）
└─ 过滤规则 Filter Rule（基于业务对象属性）
```

### **3.2 角色体系**

| 角色 | 级别 | 说明 |
| :--- | :--- | :--- |
| **系统管理员** | 系统级 | 系统中权限最高的用户，拥有系统全部管理权限，包括用户管理、系统配置、审计权限分配、**存储配额上限调节**等 |
| **审计人员** | 系统级 | 拥有查看审计日志的权限，查看范围（普通用户/企业用户/全部）由系统管理员分配 |
| **普通用户** | 系统级 | 注册后的默认身份，可使用个人空间，可创建或加入企业 |
| **企业所有者 Owner** | 企业级 | 创建企业的人，默认拥有企业全部权限，可转让企业 |
| **企业管理员 Admin** | 企业级 | 由所有者或管理员任命，拥有企业管理和资源管理权限 |
| **企业普通成员 Member** | 企业级 | 企业内的普通成员，通过分组或直接授权获得资源权限 |
| **分组管理员 Group Leader** | 分组级 | 某个分组的管理员，可管理本组成员，但不可创建分组或分配资源权限（除非另有授权） |

**说明：**

- 系统管理员与审计人员为系统内置角色，不与企业绑定，一个用户可以被授予系统角色（特殊认证）。
- 企业所有者也属于企业管理员范畴。
- 一个用户可以同时是多个企业的成员，在不同企业中角色可以不同。
- 一个用户在同一企业内可以属于多个分组，权限取最高。
- 分组管理员可通过管理授权获得，并可进一步被授权管理其他分组（分级授权）。
- 审计人员的查看范围可由系统管理员灵活配置，可限定为仅查看普通用户日志、仅查看企业用户日志、或者全量查看。

### **3.3 资源与权限模型概述**

- 资源采用 **树状层级** 结构：资料库为顶层容器，其下可包含文件夹和文件；文件夹下可再包含子文件夹和文件。
- 每类资源均支持 **读（READ）**、**写（WRITE）**、**所有权（OWNER）** 三种权限。
- 所有权（OWNER）作为**独立的关系**进行管理：一个资源可被 **多个用户或企业** 共同拥有，所有权可在用户/企业之间 **转让**，并受 **有效期** 约束（起始可用日期必填，未设置过期时间则一直有效）。
- 权限可以授予 **分组** 或 **用户**，且支持 **继承**：文件夹从其上级资源继承权限，文件从其所在文件夹继承权限。
- 用户最终对某个资源的权限 = 直接授权权限 ∪ 通过分组的继承权限 ∪ 从上级资源继承的权限，取最高值。
- **数据行级权限** 独立于资源权限，用于过滤资源内部的数据行，二者叠加生效。

### **3.4 管理授权模型概述**

- 企业管理员拥有全部管理权限。
- 企业管理员可创建分组，并可将某个分组的 **管理权** 授予企业内的任意成员，使其成为该分组的分组管理员。
- 分组管理员在其被授权的分组范围内拥有以下权限：
  - 查看本组成员列表。
  - 添加/移除本组成员。
  - 管理本组内成员的角色（例如将成员设为分组管理员，需额外授权并进行短信验证）。
- 分组管理员 **不能** 创建分组、不能分配资源权限、不能修改分组基本信息，除非被企业管理员明确授予更高级的管理权限。
- 管理授权支持 **继承**：如果分组存在子分组（后续扩展），父分组管理员可以管理子分组，但当前仅一级分组，故无继承场景。

### **3.5 系统级权限模型概述**

- 系统管理员具有最高权限，可进行：
  - 管理所有用户（查看、禁用、注销、恢复等）。
  - 配置系统参数。
  - 分配审计人员权限（包括授予/撤销审计角色、设置审计日志查看范围）。
  - 查看全部审计日志（系统管理员本身也能查看审计日志）。
- 审计人员拥有审计日志查看权限，其权限范围由系统管理员设定：
  - **查看普通用户日志**：可查看系统中所有普通用户（非企业用户、非系统用户）的审计日志。
  - **查看企业用户日志**：可查看所有企业用户的审计日志（在企业内的操作日志）。
  - **查看全部日志**：可查看上述两者，但不包括系统用户的敏感操作日志（可由系统管理员单独控制）。
- 审计人员权限可动态调整，立即生效。

## **4. 用户与认证详细设计**

### **4.1 用户账号模型**

用户账号是全局唯一的。用户基础信息不区分"普通用户"和"企业用户"，企业身份通过企业成员关系 `company_members` 来决定。系统用户则通过额外的系统角色表进行标记。

用户主要字段：
- 用户 ID `user_id`
- 用户编号 `user_no`
- **手机号 `phone`**（用户主手机号，作为核心联系属性，用于展示、通知接收，以及管理员变更等敏感操作时的手机短信验证码校验）
- 昵称 `nickname`
- 头像 `avatar_url`
- 状态 `status`：正常、禁用、注销
- 系统角色 `system_role`：可选，如 SYSTEM_ADMIN / AUDITOR / NONE
- 创建时间 `created_at`
- 更新时间 `updated_at`

认证标识独立存储，支持一个用户绑定多种登录方式。

### **4.2 认证标识模型**

认证方式：
- 手机号：已通过短信验证码验证的手机号。
- 微信：微信 unionid 或 openid。

一个用户可以拥有：
- 一个手机号认证
- 一个或多个微信认证（本设计按一个微信认证处理）

登录标识表 `user_auths` 设计：

| 字段 | 说明 |
| :--- | :--- |
| `user_id` | 用户 ID |
| `auth_type` | 认证类型：PHONE / WECHAT |
| `identifier` | 手机号或微信 unionid/openid |
| `credential` | 密码哈希，微信认证可为空 |
| `verified_at` | 认证通过时间 |
| `status` | 状态：ACTIVE / DISABLED |

唯一约束：`(auth_type, identifier)`，保证一个手机号或微信只能绑定一个用户。

### **4.3 用户状态机**

用户状态流转：

```text
ACTIVE ──禁用──> DISABLED ──恢复──> ACTIVE
  │
  └──注销──> CANCELLED
```

说明：
- 禁用用户不能登录。
- 注销用户数据按合规要求保留或删除。
- 系统管理员可以手动将用户设为禁用或注销。

### **4.4 注册流程**

#### **4.4.1 手机号验证码注册**

流程：
1. 用户输入手机号，请求发送验证码。
2. 系统校验手机号是否已注册：
   - 已注册：提示直接登录。
   - 未注册：发送短信验证码。
3. 用户输入验证码和密码。
4. 系统校验验证码：有效、未过期、未消耗、错误次数未超限。
5. 创建用户账号，并在 `users` 主表中写入 `phone` 字段。
6. 创建手机号认证记录 `user_auths(auth_type=PHONE, identifier=手机号, credential=密码哈希)`。
7. 登录成功，返回 JWT Token。

要求：
- 密码需满足强度要求，例如至少 8 位，包含字母和数字。
- 密码使用 bcrypt/argon2 等安全算法加密存储。

#### **4.4.2 微信快速注册**

流程：
1. 用户在客户端发起微信扫码注册。
2. 系统生成微信 OAuth 二维码，包含一次性 `state`。
3. 用户扫码并授权，微信回调携带 `code` 和 `state`。
4. 系统校验 `state` 有效性。
5. 通过 `code` 调用微信接口换取 `unionid/openid`。
6. 系统检查该微信是否已绑定用户：
   - 已绑定：直接登录。
   - 未绑定：进入手机号绑定流程。
7. 用户输入手机号并获取短信验证码。
8. 系统校验验证码。
9. 检查手机号是否已注册：
   - 已注册：提示用户该手机号已有账号，是否将微信绑定到已有账号。
   - 未注册：创建新用户，填入 `phone` 字段，绑定手机号和微信。
10. 用户可设置登录密码，也可以跳过。若跳过，则后续只能通过微信扫码登录，需在个人中心设置密码后才能使用手机号密码登录。
11. 注册完成，返回 JWT Token。

说明：
- 微信注册时必须提供手机号。
- 如果产品要求严格，可将设置密码设为必填。

### **4.5 登录流程**

#### **4.5.1 手机号 + 密码登录**

流程：
1. 用户输入手机号和密码。
2. 系统通过 `user_auths(auth_type=PHONE, identifier=手机号)` 查找认证记录。
3. 校验密码哈希。
4. 校验用户状态是否为 ACTIVE。
5. 登录成功，返回 JWT Token。

#### **4.5.2 微信扫码登录**

流程：
1. PC 端展示微信登录二维码。
2. 系统生成一次性 `state`，标记场景为 `LOGIN`。
3. 用户使用微信扫码并授权。
4. 微信回调携带 `code` 和 `state`。
5. 系统校验 `state`。
6. 通过 `code` 换取微信 `unionid/openid`。
7. 系统查找 `user_auths(auth_type=WECHAT, identifier=unionid/openid)`：
   - 找到：登录成功。
   - 未找到：进入绑定/注册流程。
8. 绑定/注册流程：
   - 用户输入手机号 + 短信验证码。
   - 如果手机号已注册：将微信绑定到已有账号。
   - 如果手机号未注册：创建新账号并绑定微信与手机号（写入主表 `phone`）。
9. 返回 JWT Token。

### **4.6 账号绑定与解绑**

#### **4.6.1 绑定微信**

已登录用户可在"账号安全"中绑定微信：
1. 用户扫码授权。
2. 系统校验微信是否已被其他账号绑定。
3. 如未绑定，则创建 `auth_type=WECHAT` 记录。

#### **4.6.2 绑定与更换手机号**

已登录用户可绑定或更换手机号：
1. 用户输入新手机号 + 短信验证码。
2. 校验手机号未被其他账号绑定。
3. 更新 `users` 主表中的 `phone` 字段。
4. 创建或更新对应的 `auth_type=PHONE` 记录。

#### **4.6.3 解绑**

- 用户至少需要保留一种登录方式。
- 解绑手机号后，手机号密码登录不可用。
- 解绑微信后，微信扫码登录不可用。

### **4.7 密码重置流程（忘记密码）**

#### **4.7.1 手机号验证码重置密码**

适用场景：用户忘记密码，无法通过手机号密码登录。

流程：
1. 用户在登录页点击"忘记密码"，输入已注册手机号。
2. 系统校验手机号已注册且账号状态正常（ACTIVE）。
3. 系统向该手机号发送短信验证码，场景为 `RESET_PWD`；未注册手机号提示"该手机号未注册"。
4. 用户输入验证码与新密码。
5. 系统校验验证码：存在、未过期、未消耗、尝试次数未超限、匹配正确；校验通过后标记为已消耗。
6. 系统校验新密码强度（≥ 8 位，包含字母和数字）。
7. 系统更新 `user_auths` 中该手机号对应的 PHONE 认证记录密码哈希（bcrypt 重新加密）。
8. 密码重置完成，用户可使用新密码登录。

要求：
- 仅支持已注册且绑定手机号密码认证（`user_auths` 存在 `auth_type=PHONE` 记录）的账号。
- 新密码需满足强度要求（至少 8 位，包含字母和数字）。
- 重置成功后**不自动签发 Token**，引导用户使用新密码重新登录，避免异常场景下的会话污染。
- 与注册一致的安全策略：验证码 5 分钟有效、同一手机号 60 秒发送限频、最多 5 次错误尝试、一次性使用。
- 账号处于禁用 / 注销状态时禁止重置。

### **4.8 消息中心设计**

#### **4.8.1 概述**

每个用户拥有独立的消息中心，用于接收系统消息。登录后可在消息中心查看消息、标记已读、查看未读数量。

系统在以下业务场景**自动**向相关用户推送站内消息：
- **用户申请加入企业** → 向企业**全部管理员**（OWNER / ADMIN）发送「申请消息」（`JOIN_REQUEST`）；
- **企业管理员邀请用户加入** → 向**被邀请用户**发送「邀请消息」（`INVITATION`）；
- **系统运营消息** → 由系统管理员向指定用户发送「系统消息」（`SYSTEM`）。

> **短信通知扩展说明**：当前版本**不通过短信发送额外的提醒**，消息仅通过站内消息中心触达。数据库预留 `sms_notified` 字段与发送扩展点，后续接入短信网关后，在消息发送时同步发送短信提醒并标记 `sms_notified=1`。

#### **4.8.2 消息模型（`user_messages` 表）**

| 字段 | 说明 |
| :--- | :--- |
| `message_id` | 消息 ID（主键） |
| `user_id` | 接收者用户 ID |
| `message_type` | 消息类型：`SYSTEM`（系统消息）、`JOIN_REQUEST`（申请加入企业）、`INVITATION`（企业邀请加入） |
| `title` | 消息标题 |
| `content` | 消息正文（含企业名 / 用户昵称等） |
| `related_company_id` | 关联企业 ID（申请 / 邀请消息填充） |
| `related_user_id` | 关联用户 ID（申请发起人 / 邀请发起人） |
| `is_read` | 是否已读：0-未读，1-已读 |
| `read_at` | 已读时间 |
| `sms_notified` | 短信通知标记：0-未发短信（当前固定），1-已发短信（后续短信通道接入后） |
| `created_at` | 消息创建时间 |

#### **4.8.3 消息类型与内容约定**

| `message_type` | 触发场景 | 接收者 | 内容示例 |
| :--- | :--- | :--- | :--- |
| `JOIN_REQUEST` | 用户申请加入企业 | 企业全部管理员（OWNER / ADMIN） | 「用户【张三】申请加入企业【示例公司】，请前往成员管理处理」 |
| `INVITATION` | 管理员邀请用户加入 | 被邀请用户 | 「企业【示例公司】邀请您加入，请前往消息中心确认」 |
| `SYSTEM` | 系统 / 管理员主动发送 | 指定用户 | 由系统管理员配置 |

#### **4.8.4 接口约定**

| 接口 | 说明 |
| :--- | :--- |
| `GET /api/messages` | 分页查询我的消息 |
| `GET /api/messages/unread-count` | 未读消息数 |
| `PUT /api/messages/{messageId}/read` | 标记单条消息已读 |
| `PUT /api/messages/read-all` | 全部标记已读 |
| `POST /api/companies/{companyId}/members/apply` | 用户申请加入企业（触发 `JOIN_REQUEST` 消息） |
| `POST /api/companies/{companyId}/members/invite` | 企业管理员邀请用户加入（触发 `INVITATION` 消息） |

## **5. 企业与成员设计**

### **5.1 企业模型**

企业是资源隔离和管理的单元。企业主要字段：
- 企业 ID `company_id`
- 企业编号 `company_no`
- 企业名称 `name`
- 企业 Logo `logo_url`
- 所属者用户 ID `owner_user_id`
- 企业状态 `status`：ACTIVE / DISABLED / DISSOLVED

创建企业：
- 任何已登录用户可以创建企业。
- 创建者默认成为企业所有者 `OWNER`。
- 企业创建后自动生成企业成员关系。

企业生命周期（v3.5 起）：
- **注销 / 所有权转让需审批**：企业所有者发起注销或所有权转让后，须经**系统管理员或有权限的审计人员**批准后方可生效。
- 未获批准的申请保持待审批状态，企业维持正常经营；批准后企业状态置为 `DISSOLVED`（注销）或完成所有者变更（转让）。

### **5.2 企业成员角色**

企业成员角色枚举：

| 角色 | 标识 | 说明 |
| :--- | :--- | :--- |
| **所有者** | OWNER | 企业创建者，拥有全部权限，可转让企业 |
| **管理员** | ADMIN | 企业管理员，拥有企业管理和资源管理权限 |
| **普通成员** | MEMBER | 企业普通成员，通过分组或直接授权获得资源权限 |

说明：
- 一个企业只有一个所有者，但可以转让。
- 一个企业可以有多个管理员。
- 企业管理员与所有者统称"企业管理员"，在权限判断中等价。

### **5.3 成员状态机**

企业成员状态流转：

```text
                 ┌──批准（企业所有者/管理员）──> ACTIVE ──禁用──> DISABLED
INVITED ──申请/邀请──┤
                 └──拒绝──> EXITED
```

说明：
- 管理员可邀请用户加入企业。
- 邀请时如果用户已注册，则直接进入邀请列表，用户接受后成为 ACTIVE。
- 邀请时如果用户未注册，可发送短信邀请，注册后自动成为 ACTIVE。
- 用户被禁用后无法访问企业资源。
- **消息联动**：用户申请加入企业时，系统自动向企业全部管理员发送申请消息（`JOIN_REQUEST`）；企业管理员邀请用户加入时，系统自动向被邀请用户发送邀请消息（`INVITATION`）。当前不通过短信额外提醒，后续接入短信通道后再补发短信。
- **申请审批（v3.5）**：用户申请加入企业后，成员状态为 `INVITED`（待审批），须由**企业所有者或管理员批准**后才变为 `ACTIVE`；被拒绝则变为 `EXITED`。

### **5.4 企业管理员权限**

企业管理员拥有以下权限：
- 管理企业信息。
- 邀请、移除、禁用企业成员。
- **设置与变更企业管理员（高危操作，必须通过当前管理员手机短信验证码校验）**。
- 创建、编辑、删除分组。
- 分配资源权限（包括直接授权给用户或分组）。
- 设置数据行级权限规则。
- 管理企业资源（资料库、文件夹、文件）。
- 查看企业所有资源。
- 管理授权：将分组管理权授予其他成员。

企业所有者额外权限：
- **发起**企业所有权转让申请（须经系统管理员或有权限的审计人员批准后生效）。
- **发起**企业注销申请（须经系统管理员或有权限的审计人员批准后生效）。

## **6. 分组与资源权限设计**

### **6.1 分组模型**

分组是企业内的组织单元，支持树状层级结构，但当前阶段仅允许 **一级分组**，即分组下不能再创建子分组。设计上通过 `parent_group_id` 字段预留层级扩展能力。

分组主要字段：
- 分组 ID `group_id`
- 所属企业 ID `company_id`
- 父分组 ID `parent_group_id`（当前必须为 NULL，表示一级分组）
- 分组名称 `name`
- 分组描述 `description`
- 分组状态 `status`：ACTIVE / DISABLED
- 创建人 `created_by`
- 创建时间 `created_at`

分组规则：
- 当前仅支持一级分组，即创建时 `parent_group_id` 必须为 NULL。
- 只有企业管理员可以创建分组。
- 分组管理员可以管理本组成员，但不能创建子分组、不能修改分组基本信息、不能分配资源权限。
- 后续扩展为树状结构时，只需开放 `parent_group_id` 的赋值限制，并增加层级校验即可。

### **6.2 分组管理员与分级授权**

一个分组可以有多个分组管理员。分组管理员通过 **管理授权** 机制产生。

**管理授权模型**：企业管理员（或所有者）可以将某个分组的 **管理权** 授予企业内的任意成员，该成员即成为该分组的分组管理员。设置或修改分组管理员属于角色提权与变更，同样需要触发当前操作管理员的手机短信验证码二次校验。

管理授权记录包含：

| 字段 | 说明 |
| :--- | :--- |
| `delegation_id` | 授权 ID |
| `company_id` | 企业 ID |
| `group_id` | 被管理的分组 ID |
| `grantee_user_id` | 被授权用户 ID |
| `granted_by` | 授权人用户 ID |
| `scope` | 授权范围：GROUP_MANAGE（管理该分组及成员） |
| `created_at` | 授权时间 |

分组管理员权限：
- 查看本组成员列表。
- 添加/移除本组成员。
- 设置本组成员为分组管理员（需存在相应授权，并完成短信验证）。
- 不能创建分组。
- 不能分配或修改资源权限。
- 不能修改分组名称、描述等企业级信息。

### **6.3 资源模型**

资源采用 **统一资源模型**，支持三种类型：资料库（Library）、文件夹（Folder）、文件（File）。资源之间存在父子关系，构成树状层级。

资源主要字段：
- 资源 ID `resource_id`
- 资源编号 `resource_no`
- 资源名称 `name`
- 资源类型 `resource_type`：LIBRARY / FOLDER / FILE
- 父资源 ID `parent_resource_id`：对于资料库为 NULL，文件夹和文件指向其上级资源
- 创建人 `creator_user_id`（仅记录创建者，不代表唯一所有者）
- 状态 `status`：ACTIVE / ARCHIVED / DELETED
- 创建时间 `created_at`
- 更新时间 `updated_at`

**资源所有权（`resource_owners`）** 作为独立的关联关系维护，与资源本身分离，字段如下：
- 所有者类型 `owner_type`：USER / COMPANY
- 所有者 ID `owner_id`：用户 ID 或企业 ID
- 起始可用日期 `valid_from`：**必填**
- 过期时间 `valid_until`：可选，**为空表示一直有效**
- 授权/转让来源 `granted_by`
- 状态 `status`：1-有效，0-已撤销/已转让
- 创建时间 `created_at`：所有权关系的创建时间
- 更新时间 `updated_at`：所有权关系的最近变更时间

说明：
- 一个资源可被**多个用户或企业共同拥有**（`owner_type + owner_id` 组合）。
- 所有权支持**转让**：由原所有者发起，转让后目标用户/企业成为新所有者。
- 所有权受**有效期**约束：仅在 `valid_from ~ valid_until` 之间有效；`valid_until` 为空则永久有效。
- 资源层级：资料库下可包含文件夹和文件；文件夹下可包含子文件夹和文件。
- 资源权限可以授予分组或用户，支持 **继承**。
- **存储配额**：个人 / 企业资源的存储占用设有上限（个人默认 200MB、企业默认 10GB，以字节为单位）；超过配额时禁止继续创建文件，上限由系统管理员通过系统参数调节（详见 2.4）。
- **所有权归属（v3.5）**：**企业用户创建资源时，可指定资源所有权属于个人还是企业**：
  - 归属个人（`owner_type=USER`）：资源登记为该用户所有，占用**个人存储配额**；
  - 归属企业（`owner_type=COMPANY`）：资源登记为该企业所有，占用**企业存储配额**，创建者须为该企业成员；
  - 系统按所选归属登记初始所有者（起始可用日期=创建时间，永久有效）。

### **6.4 权限类型**

资源权限分为三种：

| 权限 | 标识 | 说明 |
| :--- | :--- | :--- |
| **读权限** | READ | 可以查看、下载资源内容 |
| **写权限** | WRITE | 可以新增、编辑、上传资源内容，包含读权限 |
| **所有权** | OWNER | 拥有资源全部操作权限，包括读、写、删除、分享等，包含读和写权限 |

权限优先级：OWNER > WRITE > READ

> 说明：**所有权（OWNER）** 作为一种正式的资源关系，由「资源所有者（`resource_owners`）」维护，支持**多所有者、转让与有效期控制**；资源所有者自动拥有该资源的全部操作权限。`resource_permissions` 中的 OWNER 级别授权用于将完整操作权限显式授予某用户或分组（不改变所有权关系）。

> **授权有效期**：`resource_permissions` 中的 **读、写、所有权授权同样通过起始可用日期与过期时间控制有效期**——起始可用日期 `valid_from` 必填；过期时间 `valid_until` 可选，未设置则一直有效；超过过期时间后，对应授权自动失效。

> **所有权分享后的原所有者权限（v3.6）**：个人用户将资源所有权**分享（转让）给企业**后，原个人用户的所有权自动撤销；**企业管理员**（资源新所有者的企业管理员）可将原所有者的访问权限调整为以下三种之一：
> - **无权（NONE）**：不授予任何权限，原用户无法访问该资源；
> - **只读（READ）**：原用户仅可查看 / 下载；
> - **可写（WRITE）**：原用户可新增 / 编辑 / 上传（含读权限）。
> 该调整通过 `resource_permissions` 授权记录实现（READ / WRITE 授权，起始可用日期为当前时间、永久有效；NONE 即撤销该用户在该资源上的全部授权）。

### **6.5 授权与继承**

#### **6.5.1 授权主体**

资源权限的授权主体支持 **分组** 和 **用户** 两种类型。

#### **6.5.2 继承规则**

- 资源创建者默认成为资源的**所有者**（起始可用日期为创建时间，永久有效）。
- 企业创建的资源，企业默认成为资源所有者，企业管理员拥有该资源全部操作权限。
- 个人资源默认由创建者个人所有。
- 资源所有者自动拥有该资源的全部操作权限（等同 OWNER）。
- 企业的子资源默认继承父级资源的权限；如果有单独授权，则与继承权限合并取最高值。
- 资源权限（READ / WRITE / OWNER）的**每条授权均带有效期**：起始可用日期 `valid_from` 必填，过期时间 `valid_until` 可选（为空一直有效）；权限合并时仅统计**处于有效期内**的授权。

#### **6.5.3 数据行级权限**

数据行级权限用于在资源内部对业务数据行进行过滤。例如根据地区、行业等自定义规则进行并集合并查询。

#### **6.5.4 所有权管理**

- **多所有者**：一个资源可被多个用户或企业共同拥有，每位所有者的有效性独立计算。
- **所有权转让**：资源所有者可将所有权转让给其他用户或企业；转让成功后，原所有者失去该资源的所有权（除非原所有者同时通过其他所有权关系继续拥有）。
- **有效期规则**：
  - 起始可用日期 `valid_from` 为**必填项**；
  - 过期时间 `valid_until` 为可选项，**未设置则一直有效**；
  - 超过过期时间后，对应的所有权关系自动失效。
- 权限判定时，仅**处于有效期内的所有者**计为有效所有者，自动获得 OWNER 权限。

### **6.6 权限判定流程**

权限判定分为 **所有权判定**、**资源权限判定** 和 **数据行级权限判定**：

- **所有权判定**：处于有效期内（`valid_from` ≤ 当前时间，且 `valid_until` 为空或 ≥ 当前时间）的资源所有者视为有效所有者，自动获得 OWNER 权限。
- **资源权限判定**：对非所有者的用户，按 `resource_permissions` 的直接授权与分组继承、上级资源继承权限合并取最高值；仅统计**处于有效期内**（`valid_from` ≤ 当前时间，且 `valid_until` 为空或 ≥ 当前时间）的授权记录。
- **数据行级权限判定**：在通过资源权限的基础上，对数据行进行过滤。

### **7.1 手机号验证码注册**

**用例编号**：UC-001  
**用例名称**：手机号验证码注册  
**参与者**：普通用户（未注册）  
**前置条件**：
- 用户手机号未注册。
- 用户能够接收短信。

**主流程**：
1. 用户在注册页面输入手机号，点击"获取验证码"。
2. 系统校验手机号格式正确，且未注册。
3. 系统生成验证码并发送短信，记录验证码哈希、过期时间、场景为 REGISTER。
4. 用户输入收到的验证码和设置的密码。
5. 系统校验验证码：存在、未过期、未消耗、尝试次数未超限、匹配正确。
6. 系统创建用户账号（`users` 表，写入 `phone` 字段）。
7. 系统创建手机号认证记录（`user_auths`），存储手机号、密码哈希，状态 ACTIVE。
8. 系统标记验证码为已消耗。
9. 系统生成 JWT Token 并返回给客户端。
10. 用户完成注册并自动登录。

**后置条件**：
- 用户账号创建成功，`users` 表存有手机号。
- 手机号认证绑定成功。
- 用户状态为 ACTIVE。

4. 操作者点击“发送验证码”，系统向操作者 `users` 表中的 `phone` 发送短信验证码，并记录验证码哈希、过期时间及场景 `ADMIN_ROLE_CHANGE`。
5. 操作者输入收到的短信验证码，点击确认提交。
6. 系统校验验证码：存在、未过期、未消耗、尝试次数未超限、匹配正确。
7. 系统校验通过后，更新目标成员在 `company_members` 表中的角色字段（更新为 ADMIN 或 MEMBER）。
8. 系统标记该验证码为已消耗。
9. 系统自动记录高危操作审计日志（包含操作人 ID、目标人 ID、原角色、新角色、校验时间等）。
10. 系统返回变更成功提示，并向目标用户发送角色变更通知。

**后置条件**：
- 目标成员的角色更新完成并立即生效。
- 产生对应的安全审计日志。

**异常流程**：
- 验证码错误：提示重新输入，错误次数达 5 次后当前验证码失效。
- 验证码超时：提示验证码已过期，请重新获取。
- 操作者手机号为空或未绑定：提示“操作者账号缺少安全验证手机，请先完善个人中心手机绑定”。
- 尝试取消企业所有者（OWNER）的角色：拒绝并提示“企业所有者角色不可直接更改，请先进行企业所有权转让”。

**备注**：
- 验证码有效期 5 分钟，同一手机号 60 秒内仅能发送一次。

### **7.33 企业注销 / 所有权转让审批**

**用例编号**：UC-033  
**用例名称**：企业注销 / 所有权转让审批  
**参与者**：系统管理员或有权限的审计人员（审批人）  
**前置条件**：
- 操作者为企业所有者（OWNER），状态 ACTIVE。
- 存在待审批的企业变更申请（`company_approvals`，类型 `DISSOLVE` 或 `TRANSFER`）。
- 审批人为**系统管理员**，或**有权限的审计人员**（审计范围覆盖该企业：`audit_scope` 为 `ALL` 或 `ENTERPRISE_USERS`，且 `scope_details.allowed_company_ids` 未限定或包含该企业）。

**主流程**：
1. 企业所有者发起**企业注销**或**所有权转让**申请，系统创建待审批记录（`company_approvals`）。
2. 系统管理员或有权限的审计人员在系统管理 / 审批中心查看待审批申请。
3. 审批人选择「批准」或「拒绝」并填写意见。
4. **批准**：
   - 注销申请：企业状态置为 `DISSOLVED`，相关企业成员、分组、资源关系归档 / 清空；
   - 转让申请：企业所有者更新为目标用户，原所有者角色调整为普通成员（或按规则处理）。
5. **拒绝**：申请状态置为 `REJECTED`，企业维持正常状态。

**后置条件**：
- 审批通过后变更立即生效；拒绝后申请失效，企业维持原状。

**异常流程**：
- 审批人无权限（非系统管理员且审计范围不含该企业）：提示无权限。
- 申请不存在或已处理：提示申请不存在或已处理。

### **7.34 企业管理员调整原所有者访问权限**

**用例编号**：UC-034  
**用例名称**：企业管理员调整原所有者访问权限  
**参与者**：企业管理员（资源新所有者）  
**前置条件**：
- 个人用户已将资源所有权**分享（转让）**给企业，企业为该资源的有效所有者。
- 操作者为企业管理员（企业成员角色 OWNER / ADMIN，状态 ACTIVE）。

**主流程**：
1. 企业管理员选择原个人用户与目标访问级别：**无权（NONE）/ 只读（READ）/ 可写（WRITE）**。
2. 系统校验操作者为该资源的有效所有者、目标用户**曾为该资源的个人所有者**（所有权已转让 / 撤销）。
3. **无权（NONE）**：系统撤销原用户在该资源上的全部授权记录，原用户无法访问。
4. **只读（READ）/ 可写（WRITE）**：系统为该用户创建（或更新）对应 READ / WRITE 授权，起始可用日期为当前时间、永久有效。

**后置条件**：
- 原用户的资源访问权限立即更新。

**异常流程**：
- 操作者不是资源有效所有者：提示无权限。
- 目标用户不是该资源的原所有者：提示"目标用户不是该资源的原所有者"。
